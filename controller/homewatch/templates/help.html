About homewatch

A self-hosted monitor for your home: internet line, servers, network, backups and UPS, with notifications when something needs attention. It only reads from your devices and never changes them.

Install

You need a Linux host with Docker Engine and the Compose plugin (2 CPU, 2 GB RAM and 10 GB disk are plenty). Download docker-compose.yml, Caddyfile, env.example and install.sh from the latest release, then:

mkdir homewatch && cd homewatch
chmod +x install.sh
less install.sh          # please read it first; it's short
./install.sh

The script writes .env with a new master key, creates a self-signed certificate and starts the containers. It prints the certificate's SHA-256 fingerprint: compare it when your browser warns about the certificate at https://<host>.

The script also prints a one-time setup code, which the wizard asks for, so nobody else on your network can claim homewatch first. A new code is made each time homewatch restarts or is reset, and only the newest works. To see it, run docker compose logs controller | grep "setup code" | tail -1.

The setup wizard then asks for an admin account, your home's name and time zone, the internet checks and contracted speed, your equipment, a notification channel and an optional heartbeat. Under "Your equipment" you tick what you have; the wizard then opens each module's page in turn so you can connect it, or skip it. Anything else you add later, one module at a time, under Modules.

How alerts work

  • Confirmation: a change must hold for 2 runs (about 4 minutes) before it's sent, so short blips stay quiet.
  • Reminders: open problems are repeated every 12 hours. Change this, the confirmation and how often checks run under Timing on the Notifications page.
  • Offline queue: messages that can't be sent while the line is down go out when it's back, with the outage times.
  • Snooze: holds one check's notifications for a while, from Maintenance or next to the problem on Status. The history is still recorded.
  • Maintenance windows: hold notifications for chosen checks, once or every week.
  • Status page: one tile per module, coloured by its worst check. Click one to see its checks. One stays open at a time, until you close it, open another or reload the page.
  • History: a timeline of every problem and its return to OK, by module, level and period.

Notifications

  • Telegram: a bot token and chat ID.
  • ntfy: one topic URL.
  • Email: any SMTP server. Port 465 uses TLS, other ports STARTTLS; a password is never sent unencrypted.
  • Webhook: every message is POSTed as JSON with text, content, title, body, level and level_name. It works as-is with Slack, Mattermost, Rocket.Chat and Discord.
  • healthchecks.io heartbeat: homewatch pings it after every run, and healthchecks.io alerts you when the pings stop, for example when the host, power or internet is down.
  • Quiet hours per channel: warnings wait until they end; errors are always sent.
  • Weekly report: optional; pick the day, the time and the channels.

Settings and accounts

  • Accounts: an admin can change everything; a viewer can only see status, history and this page.
  • Configuration versions: every saved change is kept (last 200), showing who changed what. Each can be viewed and restored, and a restore can itself be undone.
  • Export and import: System downloads all settings as one YAML file, and one is written every night (last 14 kept). Importing replaces the settings; the previous ones stay under Configuration versions. Import and restore first show what would change and which credentials would be deleted, and ask for your password.
  • Passwords, tokens and users are never part of a version or an export. Enter them again after importing elsewhere.

Update and back up

To update, set HW_VERSION in .env to the new release, then run:

docker compose pull && docker compose up -d

Database changes apply on start. The System page tells you when a newer release exists.

To back up, keep the Docker volumes homewatch_hw-data (settings, users, history, encrypted secrets) and homewatch_vm-data (metrics), and a copy of .env. Without HW_MASTER_KEY from that file, saved passwords and tokens can't be decrypted and you would enter them again.

Backup and recovery

  • HW_MASTER_KEY in .env decrypts every stored password and token. Keep a copy somewhere other than this host, such as a password manager.
  • Without that key the data still opens, but no stored credential can be read: modules show "WrongMasterKey" until you enter each credential again.
  • The README has the commands to back up and restore.

How to read the numbers

  • Internet availability counts only the time homewatch was really watching the line. Time before the install, or with homewatch or its probes down, is unknown and isn't counted as up. Monitored shows how much of the period that covers.
  • UNKNOWN on the Status page means a module has nothing to judge yet, or its reading can't be trusted.
  • A change must be seen in a new reading to count as confirmed. A module that reads rarely is read again sooner when a reading shows a change.

Security

  • Don't forward homewatch to the internet. Use it on your LAN or over a VPN such as Tailscale.
  • Give each module a dedicated read-only account, as its setup steps describe.
  • Keep "Check the HTTPS certificate" on when the device has a trusted certificate. For a self-signed one, untick it: homewatch trusts the certificate it sees at the first connection and logs in only to that one. Check the fingerprint on the module's page against the device. System lists how every device connection is protected.
  • Secrets, including ntfy topic and healthchecks.io ping addresses, are encrypted at rest, never shown again after saving and left out of exports. Passwords are hashed with Argon2. Logins lock for 5 minutes after 5 failures from one address, or 20 on one account.
  • Adding or removing a user and deleting data ask for your password again. Sessions are stored only as hashes, so a copy of the database can't be used to log in.
  • Behind a reverse proxy, name it in HW_TRUSTED_PROXIES in .env. Otherwise every visitor counts as the proxy's address for login lockouts.
  • When an import or restore changes where a credential goes, or turns off HTTPS or certificate checks, homewatch deletes that credential and switches the module or channel off until you enter it again.

Troubleshooting

What you seeWhat to do
"HTTPS certificate isn't trusted"Install a trusted certificate on the device, or untick "Check the HTTPS certificate" if it is self-signed.
ISP modem: "certificate is not the trusted one"homewatch stopped logging in to the modem. If you replaced the modem or updated its firmware, press "Trust the new certificate" on the module page. If not, check your network first: another device may be posing as the modem.
A module answers with a 503 or isn't recognizedCheck the address is the device's web GUI and includes its port, such as https://192.168.1.1:8443. Port 443 may belong to a reverse proxy.
MikroTik: "can't reach the REST API"Check that www-ssl (or www) is enabled and that this host is in its available-from list.
OPNsense: "lacks the privilege"Add the named privilege to the homewatch user under System → Access → Users.
"Probe data fresh" is in errorCheck that the Telegraf container is running. If the host's clock jumps at boot, Telegraf stalls: on a Proxmox VM, set "Use local time for RTC" to No.
The internet checks show nothingCheck that the Internet line module is enabled and at least one probe is ticked.
Home Assistant doesn't report an entityOnly essential entities are read by default. Turn on "Watch every entity" to include the rest; network RX/TX sensors are never reported.
A device's check is often down on purposeUntick it in the module's lists, or switch the check off under Checks and limits on the module's page.
